# 决策书：安卓端歌词「当前句居中」失效

- **日期**：2026-09-11
- **范围**：Hiko Flutter（`hiko/`），安卓端全屏播放页歌词层（`fullscreen_player_screen.dart::_buildLyricsView`）
- **版本基线**：1.71.1+80
- **触发**：用户报「歌曲开头高亮句能正常居中，拖进度条到后方位置就不能正确居中显示当前句」，并提出备选方案「当前句不在正中时加一个自动定位按钮」
- **定稿**：本文档给出的四条裁决已由用户逐条拍板（见「裁决」一节）

---

## 一、问题陈述

用户症状两段：①歌曲开头，高亮句落在屏幕正中心，正常；②拖动进度条到后方位置后，当前句不再居中。

用户澄清：**安卓端只有全屏播放页有歌词功能，专辑详情页没有**。因此故障界面确定为
`hiko/lib/ui/screens/fullscreen_player_screen.dart`，而非 `hiko/lib/ui/lyrics/drawer_lyrics_view.dart`。

---

## 二、实测证据

全部数据来自本机 `flutter test`（Flutter 3.47.0），合成歌词 140 行、每行 2 秒、时长 300 秒、
手机竖屏 1080×2340 @3.0（歌词区 viewport 高 418 逻辑像素）。偏差＝「当前句中心 dy − 歌词 ListView 中心 dy」的绝对值。

### 证据 1：全屏播放页 —— 中段精确，只有首尾各约 3 句偏

`hiko/test/ui/zz_sweep_test.dart`，12 个采样点冷启动跳到目标位置：

| 目标句 | 偏差 | offset | maxScrollExtent |
| --- | --- | --- | --- |
| 0 | **145.0px** | 0 | 5729 |
| 2 | **59.0px** | 0 | 5729 |
| 5 / 10 / 20 / 60 / 100 / 120 / 130 / 135 | **0.0px** | 70…5660 | 5687…5710 |
| 138 | **102.0px** | 5687 | 5687 |
| 139 | **145.0px** | 5687 | 5687 |

结论：**中段任意位置（第 5–135 句）都是 0.0px 精确居中**，1.71.1 的主体修复是有效的；
残留问题只出现在「开头／结尾各约 3 句」——列表已经顶到 `offset == 0` 或 `offset == maxScrollExtent`，
**物理上没有可滚空间**，`getOffsetToReveal` 的结果被 `clamp` 吃掉。

用户说的「拖到后方就不居中」正是这个：真实歌词文件的**最后一句往往覆盖很长的尾奏**，
所以进度条拖进歌的后段（哪怕只到 2/3）高亮的仍是最后一句，而最后一句恰恰是滚不到正中的那些。
症状因此表现为「越往后拖越不居中」，与实测吻合（偏差沿 0 → 59 → 0 → 102 → 145 的曲线两端翘起）。

### 证据 2：专辑详情页「歌词」tab —— 跳到后方时列表一动不动（已复现）

`hiko/test/ui/zz_repro_drawer_test.dart`：140 行歌词，先跟着播到第 5 句，再跳到 166s（第 83 句）。

```
[DRAWER] [跳后方 1.2s 后] active=83 autoScroll=true
[DRAWER] 跳后 offset=67.0 max=5916.0        ← 列表几乎没有移动
[DRAWER] built? 0 for 第 83 句              ← 当前句根本没进视口
[DRAWER] DEVIATION=∞ 当前句根本没进视口
```

根因（`drawer_lyrics_view.dart:27-39`）：

```dart
void _scrollToActiveLine(int index) {
  if (index < 0) return;
  final key = _lineKeys[index];
  if (key == null || key.currentContext == null) return;   // ← 静默放弃
  Scrollable.ensureVisible(context, duration: …, alignment: 0.5);
}
```

`_lineKeys.putIfAbsent(index, () => GlobalKey())` 只在 itemBuilder 里建 key，
所以**目标行从未被构建过时 `_lineKeys[index]` 就是 null**，函数啥也不做直接返回，且没有重试。
跨行远跳（拖进度条）必然落在这一支。

该文件已有 `_lineKeys`、已有远跳场景，全屏页 1.71.1 引入的「先 `jumpTo` 粗定位再重试」防护**没有同步过来**。
另外 `git show 1a9e454` 显示 1.71.1 把 `drawer_lyrics_view.dart` **整段 revert** 回旧实现（连 `hasClients` 守卫一起去掉），
该文件在 1.71.0/1.71.1 之间被反复改动，是「同一份逻辑复制成两份、各自修一半」的典型后果。

> 该界面在本轮不作为用户可见故障处理（安卓端详情页无歌词入口、用户已澄清），
> 但它是同一个缺陷的**同胞调用方**，macOS 桌面端的 `DetailDrawer` 会走到它，见裁决 R4。

### 证据 3：程序化滚动不会误关自动跟随（排除一个伪嫌疑）

Flutter SDK 里 `animateTo` 与 `applyUserOffset` 都会派发 `UserScrollNotification`
（`scroll_position_with_single_context.dart:168` `updateUserScrollDirection` → `scroll_position.dart:1074` dispatch）。
应用在 `NotificationListener` 里把 `UserScrollNotification` 一律当成「用户手动滑动」并关掉自动跟随
（`fullscreen_player_screen.dart:332-339`），理论上存在「自动滚动把自己关掉 3 秒」的自伤。

`hiko/test/ui/zz_autoscroll_flag_test.dart` 实测否定了这一点：逐句推进第 3–11 句共 9 次自动滚动，
每次 `autoScrollEnabled` 均为 `true`。**该嫌疑排除**，自动跟随开关状态是干净可信的，
可以安全地拿它当按钮的显示条件。

## 三、根因归纳

| # | 根因 | 位置 | 症状 |
| --- | --- | --- | --- |
| R1 | 列表首尾没有给「半个 viewport」的滚动余量，首末句被 `clamp` 到 0 / maxScrollExtent，永远到不了正中 | 全屏页 `padding: EdgeInsets.symmetric(vertical: 40)`（:344） | 歌开头/结尾各约 3 句偏 59–145px，**按钮点了也没反应**（无空间可滚） |
| R2 | 目标行未构建时静默 `return`，无粗定位、无重试 | `drawer_lyrics_view.dart:27-39` | 详情页歌词 tab 远跳完全不动，当前句不进视口 |
| R3 | 「滚动到当前句」逻辑在两处各写一份，1.71.0/1.71.1 因此来回误诊、反复 revert | 两文件重复实现 | 修一处漏一处，回归无覆盖 |
| R4 | 拖动进度条后不强制恢复自动跟随：若用户此前手动滑过歌词，跟随处于关闭窗口期，落地不居中 | 全屏页 `onChangeEnd`（:474） | 拖完进度条歌词停在原处，要等下一句变化才自愈 |

## 四、选项与权衡

### 选项 A：加「定位到当前句」按钮（用户原始提案）

- 否决 R1 场景下的有效性：歌末尾列表已顶在 `maxScrollExtent`，**没有可滚空间**，
  按钮按下去不会产生任何位移，用户只会得到一个「按了没反应」的按钮。
- 在 `drawer_lyrics_view.dart` 里该按钮**已经存在**（:142-157 的 `FloatingActionButton.small`），
  而它的 `onPressed` 调的正是 R2 那个静默 return 的 `_scrollToActiveLine` —— 按钮本身是哑的。
  「加按钮」这个方向在原代码里已经被试过一次，失败的正是同一个根因。
- 单独用按钮还会把「自动跟随」这个更有价值的默认行为降级成手动操作。

### 选项 B：只修 R1（首尾留白）

- 治得了「拖到后方不居中」，但拖完进度条那一刻的跟随窗口期（R4）仍在。

### 选项 C：修 R1+R2+R4，并把定位逻辑抽成一份共用实现；按钮作为补充保留

- 正面回答用户的按钮诉求（保留手动归位能力），同时把三个根因一次修掉。
- 共用实现让「再来一次 1.71.0 式误诊」在结构上不可能：改一处，两个视图同时生效。

## 五、裁决

用户逐条拍板结果：

| # | 决策点 | 裁决 | 依据 |
| --- | --- | --- | --- |
| R1 | 首尾留白 | **加首尾留白**，让首句/末句也能滚到正中 | 不加留白则「拖到后方不居中」在歌末尾必然复现，按钮也救不了 |
| R2 | 修复取向 | **修根因 + 全屏页也加按钮** | 根因必修；按钮作为用户明确要的补充保留，但**不再依赖它解决本次故障** |
| R3 | 拖完进度条的行为 | **松手即恢复自动跟随并立即居中** | 拖进度条＝「我要跳到那一刻」，落地就该看见那一刻的歌词 |
| R4 | 详情页歌词 tab | **一并修（共用同一实现）** | 同胞调用方，同缺陷；macOS `DetailDrawer` 会走到它 |

### 我替领导拍的板（用户未逐条过问，按默认执行）

| 问题 | 默认值 | 猜错的代价 |
| --- | --- | --- |
| 按钮显示条件 | 沿用「自动跟随已被关闭」这一既有语义（`!autoScrollEnabled && activeIndex >= 0`），**不做**「实时量几何判断当前句是否在正中」。证据 3 已证明该开关可信、不会闪 | 若领导要求严格按「不在正中才显示」，需每帧量几何，会引入 setState 抖动；届时可加，成本约 1 个 task |
| 按钮位置 | 全屏页右下角，现有「歌词字号」按钮**上方**，同样式胶囊容器 | 位置不满意属纯视觉，返工 5 分钟 |
| 详情页歌词 tab 的首尾留白 | **同步加上**（两份视图表现一致） | 桌面端抽屉里首末句会多出半屏留白；若嫌空可单独调小 |
| 共用实现的形式 | 一个 mixin（`lib/ui/lyrics/lyrics_auto_scroll.dart`），只共享**滚动定位**，不共享行渲染（两个视图的行样式差异大，合并渲染属另一个任务） | 形式不合口味可退化为一对自由函数，成本约 10 分钟 |
| 版本号 | 1.71.1+80 → **1.72.0+81**（新增用户可见能力＝按钮，按 minor 走） | 若领导要求走 patch，改 pubspec 一行 |

## 六、被明确否决的做法

1. **只加按钮**：R1 场景下按钮无空间可滚；R2 场景下按钮已被同一根因弄哑。加按钮不能关闭本次故障。
2. **把 `clamp` 去掉**：去掉 `clamp(0.0, maxScrollExtent)` 会让 `animateTo` 越界，滚动位置被物理层夹回，
   症状从「停在边缘」变成「抖动＋停得更边缘」，且可能触发 overscroll 弹簧效果。正解是给足滚动余量，不是取消钳制。
3. **合并两个歌词视图的渲染**：行样式差异大（详情页有角色 Badge／悬停时间点，全屏页是纯净居中大字），
   合并属大改，与本次故障无因果关系，不做。
4. **改判「用户滑动」的判据**：证据 3 表明该判据当前工作正常，无故障不改。

## 七、验收契约（供计划书引用）

- 全屏播放页：合成 140 行歌词，冷启动与拖拽两条路径下，第 0 句、第 139 句的居中偏差 `< 16px`；
  第 5–135 句继续为 `0.0px`（不得回退）。
- 拖拽路径：先跟随播放若干句，再用真实 Slider 手势拖到 55%，松手后当前句偏差 `< 16px`。
- 专辑详情页歌词 tab：跳到第 83 句后该行**必须被构建且进视口**（`findsOneWidget`），偏差 `< 16px`。
- 反向验证：把新实现临时换回旧实现（全屏页固定 40px 内边距 + 详情页静默 return），
  上述断言必须转红并贴出红输出，再还原贴全绿。
- 基线不可退：`flutter test` 用例数不低于当前基线，`skip` 数不得增加。
